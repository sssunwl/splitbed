# SplitBed 將來發展方向

2026-08-30。呢份係俾你之後慢慢研究嘅，唔係開發計劃。
所有市場判斷都係**未經驗證嘅假設**，我冇同任何真實營運者傾過。

---

## 1. 先講清楚 SplitBed 實際上解緊咩

拆走「旅舍」「床位」呢啲字之後，剩低嘅係一個好具體嘅模式：

> **一個容器裝多個唔相干嘅客戶；入面嘅內容物會令容器「上鎖」；
> 鎖會隨住時間持續同解開；被鎖住嘅剩餘容量有真實金錢成本。**

呢四樣嘢缺一不可：

| # | 條件 | 喺旅舍度即係 |
|---|---|---|
| 1 | **共用**：一個容器多個客戶 | 一間房住幾個唔識嘅人 |
| 2 | **上鎖**：內容物會限制之後可以放咩 | 有女客入咗，嗰晚就只收得女 |
| 3 | **時間**：鎖持續一段時間，空咗先解 | 住 14 晚就鎖 14 晚 |
| 4 | **有成本**：被鎖住嘅空位賣唔出＝蝕錢 | 190 個床晚／季 ＝ 約 ¥95 萬 |

**呢四條就係判斷任何新用途嘅唯一標準。** 缺一條，價值就大幅下跌；
缺兩條，就唔應該用呢套嘢。

---

## 2. 你問嘅三個方向：分房、分層、分地點

### 分房（唔分床，整間房賣）—— ⚠️ 技術上易做，但會殺死價值

整間房賣俾一張訂單，即係缺咗條件 1 同 2：冇共用、冇上鎖。
剩低嘅就只係「邊張訂單配邊間房」，變成普通嘅排程問題。

**冇 stranded bed，就冇「你唔知自己蝕緊錢」呢個洞察。**
而嗰個洞察正正就係 SplitBed 唯一嘅賣點。

技術上加呢個功能可能一日搞掂，但做完之後你手上就係一個**冇特色嘅排房工具**，
要同 Cloudbeds、Beds24 呢啲成熟 PMS 正面撞。唔建議。

### 分層 / 分區 —— ✅ 最自然嘅延伸，而且加分

樓層本身就係「房嘅容器」。而且樓層真係會有政策 ——
日韓好多酒店有**女性專用樓層**，宿舍有**男女分層**。

四條件全部保留，只係多咗一層階級：`Property → Floor → Room → Bed`。
同一套上鎖邏輯，套喺高一層。

改動：`Room` 加一個 `floorId`，policy 解析多睇一層（樓層 policy 蓋過 property、
房 policy 再蓋過樓層）。**引擎核心唔使改。**

呢個亦係做學生宿舍／員工宿舍嘅前置條件（見 §3）。

### 分地點（多間分店）—— ❌ 唔係同一個問題

「呢張訂單應該去邊間分店」係**庫存分配／路由**問題，唔係上鎖問題。
而且大部分情況客人自己揀咗地點，根本冇得調。

唯一有意義嘅情況：**員工宿舍或學生宿舍跨區分配** ——
公司真係要決定「呢 200 個新員工點分去五個宿舍」。
但嗰個係年度規劃，唔係每日操作，係另一個產品。

## 3. 其他行業：邊啲真係同一個模式

按「四條件齊唔齊」排，唔係按市場大細排。

### 第一級：四條件全齊

| 行業 | 上鎖係咩 | 點解值得睇 | 難喺邊 |
|---|---|---|---|
| **醫院病房** | 性別分艙、感染隔離（一個帶菌病人鎖住成個 bay）、專科分區 | 英國 NHS 本身就有「mixed-sex accommodation breach」呢個官方指標，即係**已經有人喺度量緊呢件事**。預算大、痛得真 | 採購週期長、涉及臨床安全、要合規。唔係一個人做得起 |
| **學生宿舍 / 員工宿舍** | 男女分層／分房、部門或年級分區 | 床位多十倍、長住客係 stranded bed 嘅元兇、政策硬性、買家係公司唔係個體戶 | 通常一年分配一次，唔係每日 —— 產品形態要改 |
| **工程營地 / 船員 / 鑽油台** | 性別、日夜更（更唔同唔應該同房）、承辦商分隔 | Hot-bedding（兩更輪住瞓同一張床）令容量計算複雜十倍，而佢哋真係好在乎 | 客戶好集中，要靠關係入 |
| **監獄 / 拘留所** | 分類（幫派、保安級別、易受傷害者） | 上鎖邏輯同旅舍一模一樣，而且係法定要求 | 極難入行，唔建議 |

### 第二級：三條件

| 行業 | 缺咗咩 / 備註 |
|---|---|
| **長者院舍 / 復康中心** | 性別 + 護理等級 + 認知障礙分區。條件齊，但決策慢、監管重 |
| **畜牧欄舍 / 實驗動物房** | 按年齡、性別、健康狀態分欄；一隻病嘅鎖住成個欄。**上鎖係字面意義上嘅污染** |
| **倉庫貨位 / 貨櫃併櫃** | 食品唔可以同化學品同櫃；散貨併唔滿就浪費艙位。條件齊，但已經有成熟軟件 |

### 第三級：睇落似，其實唔係

停車場、會議室、課室排課、器材租借 —— 呢啲只有「排程」，**冇上鎖**。
一架車走咗，個位即刻乜車都泊得。冇 stranded 概念，就冇 SplitBed 嘅價值。

**唔好因為「都係分配問題」就走去做。**

## 4. 點樣先可以被廣泛利用：三條路

### 路 A：深入一個高價值垂直

揀學生宿舍或員工宿舍（唔好一開始就攻醫院）。

- 引擎**幾乎唔使改**，加返 §2 嘅樓層層級就得
- 語言要換：唔係「旺季收入」，係「宿位使用率」同「分配公平性」
- 買家有預算、有 IT、決策集中
- 風險：分配週期由每日變成每年，**你嘅「每日打開佢」嘅理由消失咗** ——
  要重新諗產品形態

### 路 B：唔做產品，做零件

把引擎包成一個 library／API，賣俾（或者免費俾）已經有客嘅 PMS 廠商。

- 觸及面最大，獲客成本近乎零
- 你嘅引擎係零依賴 TypeScript，本身就已經係一個乾淨嘅 npm package
- 風險：買家由旅舍老闆變成開發者，**完全唔同嘅銷售方式**；
  而且你會失去同最終用戶嘅關係，長遠議價能力低

### 路 C：賣診斷，唔賣軟件

把試算器當成一份**一次性評估報告**賣俾連鎖旅舍、住宿投資方、業界顧問。

- 客單價高、唔使養客、唔使做支援
- 而家個網站已經係呢個產品，唔使再開發
- 風險：唔會 scale，係顧問生意唔係軟件生意
- **呢條路我一開始就幫你保住咗**：免費版永遠冇註冊閘，就係為咗隨時可以走呢條路

### 我嘅看法（未驗證）

短期行 C 去搵對話，同時做 §5 第 2 個實驗去試 A。B 留到有人問先做。

## 5. 最平嘅四個實驗，按成本排

### 實驗 1：問五個旅舍老闆（成本：零）
俾條 link，唔解釋。睇三樣：會唔會入自己間房嘅數字、見到個數係「哇」定「哦」、
會唔會自己撳去排房頁。

**再問一句最關鍵嘅：「你間旅舍係咪真係有男女分房？」**
好多 hostel 早就全 mixed，根本冇呢個痛點 —— 呢條問題最快篩走假需求。

### 實驗 2：換個語言試宿舍（成本：一個下午）
唔使寫任何新 code。用而家個試算器，把參數改成宿舍嘅樣：
100 床、住 120 晚、月租計、男女分層。睇下個數字仲成唔成立。

如果宿舍嘅 stranded 數字比旅舍更誇張（好可能，因為長住客多），
咁路 A 就值得認真諗。

### 實驗 3：問一個醫護朋友（成本：一餐飯）
問：「你哋病房有冇試過有空床但因為性別或者隔離而收唔到病人？」
如果對方即刻明你講咩，甚至有數據，咁就係一個真問題。
如果要解釋三次先明，就唔好諗。

### 實驗 4：把引擎放上 npm（成本：一日）
`@splitbed/engine`，零依賴，附一個 README 講清楚解決咩問題。
放咗出去唔使推廣，睇半年有冇人 star、有冇人開 issue。
零成本嘅路 B 探針。

## 6. 如果決定唔做落去

最誠實嘅收尾唔係停更，係**把試算器定型成一份可以獨立分享嘅診斷報告**，
留喺網上。佢本身已經回答緊一條真問題，就算冇人買軟件，
呢個數字對任何一個做床位住宿嘅人都有用。

而引擎、模擬器、驗證方法全部有文件，將來有人問起，
或者你自己想撿返起，唔使由零開始。
