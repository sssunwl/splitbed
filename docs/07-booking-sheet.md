# 訂單記錄表設計

2026-08-29。回答：「如果用 SplitBed，訂單記錄表該點設計？」
範例檔喺 `public/examples/`，會隨網站一齊部署，可以直接下載貼入 Google Sheet：

| 分頁 | 檔案 | 線上連結 |
|---|---|---|
| 訂單 | `splitbed-orders-example.csv` | `/splitbed/examples/splitbed-orders-example.csv` |
| 房間床位 | `splitbed-rooms-example.csv` | `/splitbed/examples/splitbed-rooms-example.csv` |
| 排房紀錄 | `splitbed-allocation-log-example.csv` | `/splitbed/examples/splitbed-allocation-log-example.csv` |

## 1. 一個原則決定咗成個設計

**Sheet 係耐用嘅紀錄，SplitBed 係快嘅工作台。兩者唔好爭做真相來源。**

- Sheet 存得耐、任何人開得、換電腦唔會冇 —— 適合做**紀錄**
- SplitBed 撳 M/F/U 快過打字、即時重算、即時睇到影響 —— 適合做**當日操作**

所以資料流係一條線，唔係一個圈：

```
訂單分頁（人手／PMS 維護）
      ↓ 匯出 CSV，貼入 SplitBed
SplitBed 排房（喺 app 內補性別、調整、鎖定）
      ↓ 匯出建議 CSV
排房紀錄分頁（只貼唔改，做耐用備份）
```

**唔好喺 Sheet 度填性別再又喺 app 填一次。** 兩個地方一定會唔同步，
而唔同步嘅時候你唔會知邊個啱。性別喺 app 撳（快），排完之後匯出返 Sheet（耐用）。

## 2. 一個檔案，三個分頁

### 分頁一：`訂單`（唯一要人手維護嘅嘢）

| 欄 | 例 | 必填 | 備註 |
|---|---|---|---|
| 訂單編號 | `BK-2027-0118` | ✅ | **見 §3，呢個欄係成個設計最重要嘅決定** |
| 來源 | `Booking.com` | | 官網／Booking.com／Agoda／Airbnb／Expedia／旅行社／Walk-in／電話／職員 |
| 訂單日期 | `2027-01-04` | | 收到訂單嗰日，唔係入住日 |
| 入住日 | `2027-02-01` | ✅ | |
| 退房日 | `2027-02-05` | ✅ | **唔住嗰晚**。2/1 入 2/5 出 = 住 4 晚 |
| 人數 | `2` | ✅ | |
| 稱謂 | `Mr` | | Mr／Ms／Mrs。**唯一可靠嘅性別來源**，見 §4 |
| 姓名 | `Tanaka Yuto` | | 訂房人。唔好用嚟猜性別 |
| 必須同房 | `是` | | 情侶／家庭填「是」，散客可以「否」 |
| 需要私人房 | `否` | | 填「是」＝成間房唔可以有其他訂單 |
| 金額 / 幣別 | `40000` `JPY` | | 排唔晒房時，用嚟決定邊張訂單優先 |
| 付款狀態 | `已付` | | 已付／部分／未付／已退 |
| 狀態 | `確認` | ✅ | 確認／已取消／No-show。**見 §5** |
| 備註 | | | |

範例：`public/examples/splitbed-orders-example.csv`

### 分頁二：`房間床位`（好少改）

| 欄 | 例 | 備註 |
|---|---|---|
| 房間代號 | `B` | |
| 床位代號 | `B04` | **一行一張床，唔係一行一間房** |
| 床位類型 | `上鋪` | 下鋪／上鋪／單人床 |
| 可男女同房 | `是` | 呢間房嘅規則 |
| 停用開始／停用結束 | `2027-02-03` `2027-02-06` | 床壞咗填呢兩格，容量自動減，唔使改成間房 |

**唔好有「房間容量」呢一欄。** 容量永遠由床數算出嚟。
加床＝加一行；減床＝填停用日期。咁樣歷史數字自然係啱嘅。

範例：`public/examples/splitbed-rooms-example.csv`

### 分頁三：`排房紀錄`（只貼唔改）

SplitBed 排完房之後撳「匯出建議 CSV」，貼落嚟。
呢個分頁係你唯一嘅**耐用**紀錄 —— 因為 SplitBed 而家啲資料只喺瀏覽器，清咗就冇。

含：訂單編號、客人序號、性別、建議房間、實際房間、鎖定、理由、匯出日期。

範例：`public/examples/splitbed-allocation-log-example.csv`

## 3. 訂單編號：整份表最重要嘅一欄

**一定要用訂房平台／PMS 自己嗰個編號，唔好自己順序編 1、2、3。**

原因唔係今日，係將來：當你接 API 自動同步訂單嗰日，
系統要靠一個**穩定嘅 key** 去認出「呢張訂單我見過」。
如果你用自己編嘅流水號，同步返嚟嘅資料就對唔返你 Sheet 入面嘅紀錄，
到時要人手逐張對，幾百張訂單就冇得救。

實務做法：

- Booking.com → 用佢個 Reservation number
- Agoda / Expedia → 用佢個 Booking ID
- 官網 / Walk-in / 電話 → 自己編，但加前綴分開，例如 `WALKIN-2027-0032`
- **同一張訂單改期唔好改編號**，改日期就得

## 4. 性別：點解唔喺 Sheet 度填

**冇任何訂房平台會俾性別資料你。** Booking.com、Agoda、Airbnb 傳過嚟嘅係
日期、人數、姓名、訂單號。而性別正正就係排房嘅關鍵輸入。

所以：

- **唯一可靠嘅預填來源係「稱謂」欄（Mr / Ms / Mrs）** —— 嗰個係客人自己填嘅真資料
- **絕對唔好用姓名去猜。** 旅舍客人嚟自世界各地，
  跨文化嘅姓名性別推測正正喺呢種場合錯得最犀利，
  而錯嘅後果係編錯一個真人嘅房
- 唔知就填「未定」。SplitBed 會只安排佢去仲未鎖定性別嘅房，
  佢自己亦唔會令嗰間房鎖定性別

**流程係：Sheet 提供骨架（日期／人數／稱謂）→ app 內十秒撳完性別 → 匯出返 Sheet 存檔。**

## 5. 已取消同 No-show 一定要留低

**唔好刪除已取消嘅訂單，改「狀態」欄就得。**

兩個原因：

1. SplitBed 已經識得跳過 `已取消` 同 `No-show` 嘅訂單 ——
   佢哋唔會佔房、唔會鎖性別、唔會被當成排唔到
2. 刪咗你就永遠唔知自己嘅取消率係幾多，
   而取消率係之後計「應該 overbook 幾多」嘅唯一依據

## 6. 三個最常見嘅填錯

| 錯 | 後果 |
|---|---|
| 退房日當成「最後一晚」 | 每張訂單多算一晚，成個排房會擠爆 |
| 日期用 `2/1` 或 `01-02-2027` | 分唔清月同日，**一律用 `YYYY-MM-DD`** |
| 改咗欄名或者調轉欄次序 | 匯入對應要重做。**加新欄請加喺最右邊** |

## 7. 將來點樣接落真正嘅訂單系統

呢份 Sheet 唔係終點，係一條有意設計嘅過渡路。三個階段，每一步都唔使推倒重來：

### 階段一（而家）：人手 Sheet → 貼 CSV
職員維護 `訂單` 分頁 → 匯出 CSV → 喺 SplitBed 撳「貼上 CSV」→ 排房。
**投入：零。**

用返上面建議嘅欄名（訂單編號／入住日／退房日／人數／稱謂／狀態），
SplitBed 會自動對應嗰六個欄，其餘欄自動設成「忽略」，唔使人手揀。
其他 PMS 格式照樣可以貼，只係要自己對應一次。
`狀態` 係 `已取消` 或 `No-show` 嘅行會自動略過，並會話你知略過咗幾多張。

### 階段二：Sheet 直接連過去
Google Sheet 用「發佈為 CSV」出一條連結，SplitBed 定時讀。
唔使每次複製貼上，但 Sheet 仍然係你嘅嘢。
**投入：細。免 OAuth、免 API key。**

### 階段三：PMS / OTA 自動同步
`訂單` 分頁由自動同步取代；`稱謂` 由 API 帶入做性別預填；
職員只需要喺 app 內確認性別。`排房紀錄` 分頁改成寫入資料庫。

**投入：大，而且每個平台要獨立做。所以要有客戶開口要先做。**
Beds24 同 Cloudbeds 嘅 API 最成熟；iCal 訂閱最易接但**冇性別亦冇人數細節**，
只可以補日期。

### 由階段一就要守住嘅三條規矩

呢三條而家唔守，將來接 API 就要重做全部歷史資料：

1. **訂單編號用平台自己嗰個**（§3）
2. **日期一律 `YYYY-MM-DD`，退房日 = 唔住嗰晚**
3. **取消單留低改狀態，唔好刪**

其他欄位改名、加減，將來都補救得返。呢三條補救唔到。
