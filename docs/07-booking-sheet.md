# 訂單記錄表設計

2026-08-29。回答：「如果用 SplitBed，訂單記錄表該點設計？」
範例檔喺 `public/examples/`，會隨網站一齊部署，可以直接下載貼入 Google Sheet：

| 分頁 | 檔案 | 線上連結 |
|---|---|---|
| 訂單 | `splitbed-orders-example.csv` | `/splitbed/examples/splitbed-orders-example.csv` |
| 房間床位 | `splitbed-rooms-example.csv` | `/splitbed/examples/splitbed-rooms-example.csv` |
| 排房紀錄 | `splitbed-allocation-log-example.csv` | `/splitbed/examples/splitbed-allocation-log-example.csv` |

## 1. 一個原則決定咗成個設計

**每個資料只有一個位放，而且要放喺系統讀得到嘅欄。**

2026-08-29 第一版犯咗個錯：把「情侶 一男一女」「女生四人團」寫喺**備註**。
文字係人睇得明，但系統讀唔到，於是同一個資料要喺 app 度再輸入一次 —— 兩個地方，必然分叉。

修正：**性別係三個獨立數字欄（男／女／未定），唔係備註。**

### 備註只准寫「唔影響排房」嘅嘢

| 應該寫 | 唔應該寫（有專屬欄位） |
|---|---|
| 23:00 後到、要求早餐、有大型行李 | 性別（用 男／女／未定） |
| 回頭客、識講廣東話、遠端工作要枱 | 人數（用 人數） |
| 餘額到埗付、平台自動退款 | 日期（用 入住日／退房日） |
| 膝頭受過傷（配合下鋪） | 「要一齊瞓」（用 盡量同房 欄） |

一句判斷法：**如果呢個資料會影響排到邊間房，佢就唔應該喺備註。**

## 2. Sheet 同 app 各自做咩

- Sheet 存得耐、任何人開得、換電腦唔會冇 —— 做**紀錄**
- SplitBed 即時重算、即時睇到影響 —— 做**當日操作**

```
訂單分頁（落單即刻填晒，包括性別）
      ↓ 匯出 CSV，貼入 SplitBed（性別直接讀到，唔使再撳）
排房（只需處理「未定」嗰幾位、調整、鎖定）
      ↓ 匯出建議 CSV
排房紀錄分頁（只貼唔改，耐用備份）
```

**新業務同接手舊 PMS 嘅分別**：
你自己收嘅單（官網／電話／walk-in），落單嗰刻就知男定女 —— 即刻填，慳返之後所有功夫。
OTA 訂單（Booking.com／Agoda）**永遠冇性別**，三個欄留空，貼完再喺 app 撳 M／F／U。
兩條路同一份表，唔使分開做。

## 2b. 訂單分頁欄位（範例：`public/examples/splitbed-orders-example.csv`）

### SplitBed 會讀嘅欄

| 欄 | 例 | 必填 | 備註 |
|---|---|---|---|
| 訂單編號 | `DIR-2027-0001` | ✅ | 見 §3 |
| 入住日 | `2027-02-01` | ✅ | `YYYY-MM-DD` |
| 退房日 | `2027-02-05` | ✅ | **唔住嗰晚**。2/1 入 2/5 出 = 住 4 晚 |
| 人數 | `2` | ✅ | |
| 男 | `2` | | **三個加埋要等於人數**，唔啱會報錯 |
| 女 | `0` | | |
| 未定 | `0` | | 未問到就填呢度，**唔好靠估** |
| 盡量同房 | `是` | | 情侶／家庭「是」，散客可以「否」。見 §4b |
| 需要私人房 | `否` | | 「是」＝成間房唔可以有其他訂單 |
| 狀態 | `確認` | | 確認／已取消／No-show，見 §5 |
| 稱謂 | `Mr` | | 只喺冇填性別欄嗰陣做預填，見 §4 |

### 你自己用、SplitBed 唔會讀嘅欄

`訂單日期`、`來源`、`聯絡人`、`聯絡方式`、`金額`、`已收`、`備註`

呢啲係你真正嘅落單紀錄。SplitBed 唔會掂佢哋，你可以照自己需要加減。

## 2c. 客人分頁（選填，需要先用）

範例：`public/examples/splitbed-guests-example.csv`

只有喺你需要**逐位客人**嘅資料先用：姓名（做 check-in）、
同一張訂單入面個別人早走、邊位要下鋪。

欄位：`訂單編號`、`客人序號`、`姓名`、`性別`、`入住日`、`退房日`、`需要下鋪`、`備註`

大部分日子唔使用。訂單分頁嘅三個性別數字欄已經夠排房。

## 2d. 房間床位分頁

範例：`public/examples/splitbed-rooms-example.csv`

一行一張床，唔係一行一間房。有 `停用開始`／`停用結束` 兩欄，
床壞咗填日期區間，容量自動減，唔使改成間房。

**唔好有「房間容量」呢一欄** —— 容量永遠由床數算出嚟，咁樣歷史數字自然係啱嘅。

## 3. 訂單編號：整份表最重要嘅一欄

**一定要用訂房平台／PMS 自己嗰個編號，唔好自己順序編 1、2、3。**

原因唔係今日，係將來：當你接 API 自動同步訂單嗰日，
系統要靠一個**穩定嘅 key** 去認出「呢張訂單我見過」。
如果你用自己編嘅流水號，同步返嚟嘅資料就對唔返你 Sheet 入面嘅紀錄，
到時要人手逐張對，幾百張訂單就冇得救。

實務做法：

- Booking.com → 用佢個 Reservation number
- Agoda / Expedia → 用佢個 Booking ID
- 官網 / Walk-in / 電話 → 自己編，但加前綴分開，例如 `WALKIN-2027-0032`
- **同一張訂單改期唔好改編號**，改日期就得

## 4. 性別：兩條來源，一個原則

**原則：知就即刻填，唔知就填「未定」，永遠唔好估。**

### 你自己收嘅單 → 落單嗰刻填

官網、電話、walk-in —— 你同客人講緊嘢，順口問一句就知。
填咗之後貼入 SplitBed，**性別直接讀到，唔使再撳一次**。

實測：15 張訂單、23 位客人，貼入去即刻 21 位已確認，
淨低嗰 2 位就係真係未問到嘅（一個 walk-in、一個 OTA 團）。

### OTA 訂單 → 冇性別，貼完再撳

**冇任何訂房平台會俾性別資料你。** Booking.com、Agoda、Airbnb 傳過嚟嘅係
日期、人數、姓名、訂單號。三個性別欄留空就得，貼完喺 app 用 M／F／U 撳，
撳完自動跳下一位。

唯一可用嘅預填係 **`稱謂` 欄（Mr／Ms／Mrs）** —— 嗰個係客人自己填嘅真資料。

### 三條硬規矩

1. **絕對唔好用姓名去猜。** 旅舍客人嚟自世界各地，
   跨文化姓名性別推測正正喺呢種場合錯得最犀利，
   而錯嘅後果係編錯一個真人嘅房。系統本身亦唔會做呢件事。
2. **男 ＋ 女 ＋ 未定 一定要等於人數。** 對唔上 SplitBed 會即刻報錯
   （例如「第 2 行：男 2 ＋ 女 0 ＋ 未定 0 ＝ 2，同人數 3 對唔上」），
   唔會亂估補數。
3. **唔好寫喺備註。** 寫喺備註等於冇填。

## 4b. 「盡量同房」係盡力而為，唔係承諾

混性別嘅情侶或朋友，喺男女分房之下**結構上冇可能同房**。
如果當成硬性要求，系統就只能拒單；當成盡力而為，系統會拆開安排，
並喺結果標示「被迫拆房」，唔會靜靜地拆完當冇事發生。

**所以要喺落訂時就管理期望。** 建議喺訂房表／自動回覆寫明：

> 我哋會盡量安排同行嘅客人同房。
> 旺季或者房間規則所限時可能需要分開安排，敬請理解。
> 如果一定要同房，請選擇私人房。

呢句嘅作用唔止係免除爭議，仲係**把「一定要同房」嘅客人導去私人房**——
嗰個係更高房價，而且對排房嚟講清晰好多。

範例訂房表：`public/examples/splitbed-booking-form-template.txt`

## 5. 已取消同 No-show 一定要留低

**唔好刪除已取消嘅訂單，改「狀態」欄就得。**

兩個原因：

1. SplitBed 已經識得跳過 `已取消` 同 `No-show` 嘅訂單 ——
   佢哋唔會佔房、唔會鎖性別、唔會被當成排唔到
2. 刪咗你就永遠唔知自己嘅取消率係幾多，
   而取消率係之後計「應該 overbook 幾多」嘅唯一依據

## 6. 三個最常見嘅填錯

| 錯 | 後果 |
|---|---|
| **性別寫喺備註** | 系統讀唔到，要喺 app 再輸入一次，兩個地方必然分叉 |
| 退房日當成「最後一晚」 | 每張訂單多算一晚，成個排房會擠爆 |
| 日期用 `2/1` 或 `01-02-2027` | 分唔清月同日，**一律用 `YYYY-MM-DD`** |
| 改咗欄名或者調轉欄次序 | 匯入對應要重做。**加新欄請加喺最右邊** |

## 7. 將來點樣接落真正嘅訂單系統

呢份 Sheet 唔係終點，係一條有意設計嘅過渡路。三個階段，每一步都唔使推倒重來：

### 階段一（而家）：人手 Sheet → 貼 CSV
職員維護 `訂單` 分頁 → 匯出 CSV → 喺 SplitBed 撳「貼上 CSV」→ 排房。
**投入：零。**

用返上面建議嘅欄名（訂單編號／入住日／退房日／人數／稱謂／狀態），
SplitBed 會自動對應嗰六個欄，其餘欄自動設成「忽略」，唔使人手揀。
其他 PMS 格式照樣可以貼，只係要自己對應一次。
`狀態` 係 `已取消` 或 `No-show` 嘅行會自動略過，並會話你知略過咗幾多張。

### 階段二：Sheet 直接連過去
Google Sheet 用「發佈為 CSV」出一條連結，SplitBed 定時讀。
唔使每次複製貼上，但 Sheet 仍然係你嘅嘢。
**投入：細。免 OAuth、免 API key。**

### 階段三：PMS / OTA 自動同步
`訂單` 分頁由自動同步取代；`稱謂` 由 API 帶入做性別預填；
職員只需要喺 app 內確認性別。`排房紀錄` 分頁改成寫入資料庫。

**投入：大，而且每個平台要獨立做。所以要有客戶開口要先做。**
Beds24 同 Cloudbeds 嘅 API 最成熟；iCal 訂閱最易接但**冇性別亦冇人數細節**，
只可以補日期。

### 由階段一就要守住嘅三條規矩

呢三條而家唔守，將來接 API 就要重做全部歷史資料：

1. **訂單編號用平台自己嗰個**（§3）
2. **日期一律 `YYYY-MM-DD`，退房日 = 唔住嗰晚**
3. **取消單留低改狀態，唔好刪**

其他欄位改名、加減，將來都補救得返。呢三條補救唔到。
