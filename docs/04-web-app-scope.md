# SplitBed 網頁小程式 — 範圍與 `/guide` 說明頁內容

Phase 1 的全部產出。純靜態，部署在 https://sssunwl.github.io/splitbed/

## 1. 三頁

### `/` What-if 模擬器（首頁）
輸入：房間與床數（可增刪）、policy（same_gender / mixed / hybrid，hybrid 可勾選哪幾間 Mixed）、
房價、季度長度、需求水平、男女比、住宿長度與 group 分佈。
輸出：三個 policy 的入住率 / 季收入 / stranded bed-nights / 被迫拆房訂單數，
含 95% 信賴區間，加一個橫向長條圖。預設值 = 札幌（2/4/3/3 床）。

**這頁是產品的鈎子。** 一個經營者五分鐘內就能看到自己場地改 policy 值幾多錢。

### `/allocator` 排房小工具
輸入：房間設定 + 訂單清單（表格手動輸入、或貼 CSV、或載入範例）。
輸出：Room × Date calendar（顯示性別 / 人數 / 容量 / 是否 flexible）、
每張訂單的建議房間、每個建議的理由文字、無法安排時的原因診斷。
可 Manual override，override 後即時顯示 impact（stranded 變化、空房數變化）。
可 export / import JSON。

### `/guide` 使用說明（內容見下 §3）

## 2. 硬性範圍界線

**做**：房間床位設定、訂單輸入、自動排房建議、calendar、manual override、
policy 切換、模擬比較、JSON/CSV import export、localStorage 保存。

**不做（Phase 1 明確不做，說明頁要寫出來）**：
登入 / 帳號 / 權限、資料庫 / 雲端同步、多間 property 同時管理、
OTA 串接、收款、房價管理 / revenue management、
Housekeeping、Waitlist、通知 / email、報表排程、
中途換房（room move）、床位層最佳化。

## 3. `/guide` 說明頁必須包含的六節

寫給**住宿經營者**看，不是寫給工程師看。全繁體中文，可加英文對照。

### 節一：SplitBed 解決什麼問題
用一個具體例子開場，不要抽象定義：

> 你有一間 3 床房，已經住了 1 位女生。今晚來了 2 位男生。
> 房間明明有 2 張空床，但你一張都賣不出。
> 這 2 張床不是「空房」，是被規則鎖住的床 —— SplitBed 叫它 stranded bed。
> 一季累積下來，札幌這種 12 床的規模大約會鎖住 187 個床晚。

然後才說：SplitBed 幫你 (a) 排房時盡量少製造這種情況，(b) 算給你看規則改了值幾多錢。

### 節二：這個網頁小程式，是整套系統的哪一部分
必須有一張圖或表，講清楚現在做了哪塊、哪塊未做：

| 整套系統 | 網頁小程式（現在） | 之後 |
|---|---|---|
| 房間 / 床位設定 | ✅ | 存進資料庫 |
| 訂單輸入 | ✅ 手動 / CSV | OTA 自動同步 |
| 自動排房建議 | ✅ | 同一個引擎 |
| Calendar | ✅ | 同上 + 多人協作 |
| Manual override + impact | ✅ | 同上 + audit log |
| What-if 模擬 | ✅ | 接真實歷史訂單 |
| 資料保存 | ⚠️ 只在你這部電腦的瀏覽器 | 雲端資料庫 |
| 多人同時用 | ❌ | ✅ |
| Check-in / 房務 | ❌ | ✅ |
| 收款 / OTA | ❌ | 視乎需求 |

並明確寫一句：
> **現階段所有資料只留在你的瀏覽器，不會上傳到任何伺服器。
> 清除瀏覽器資料就會消失，重要資料請用「匯出 JSON」保存。**

### 節三：怎樣用（三個情境，每個附截圖）
1. 「我想知改 Mixed 值唔值」→ 首頁模擬器，五步
2. 「我想幫今晚的訂單排房」→ allocator，四步
3. 「我想試下加一張床有幾大分別」→ 改床數後重跑

### 節四：已考慮到的情況（這節是信任的來源）
逐條列出，讓經營者知道系統不是玩具：

- 同一張訂單多位客人，可要求必須同房
- 混性別的情侶／朋友：same-gender 政策下結構上無法同房，系統會標示「被迫拆房」
- 性別未填（unspecified）的客人：只安排到尚未鎖定性別的房，且本身不鎖定該房
- 女性專用房 / 男性專用房 / Private room / 員工房 / 維修中房間
- 某張床壞了要停用（可設停用日期區間），容量自動減少，不需要改整間房
- 同一張訂單中個別客人早退或晚到
- 已入住的客人不會被自動搬房
- 越接近入住日，系統越不願意改動已有安排
- 重算時會盡量維持現有安排，不會每次都給你一份大搬風建議
- 無法安排時，會告訴你是哪一條規則卡住（性別 / 容量 / 必須同房 / 私人房），不是只講「失敗」
- 長住客會盡量集中，避免把整季的房間切碎
- 不會為了一個人開一間新房，除非別無選擇

### 節五：**未**考慮到的情況（同樣重要，不要隱瞞）
- 中途換房（Phase 1 一律同一間房住到尾）
- 床位層的最佳化（系統排到房，具體哪張床由你決定）
- 房價浮動 / revenue management（假設每床同價）
- 客人的社交偏好（打鼻鼾、早起、安靜房）
- 改 Mixed 後可能流失的女性客源與評分影響 —— 模型算不到，只能靠真實測試
- 模擬用的是通用旅舍需求假設，不是你自己的歷史訂單

### 節六：範例 —— 札幌改 Mixed，一季多賺幾多
直接把 `docs/05-sapporo-baseline.md` 的結論表放上去，
並附一個「用這組設定載入模擬器」的按鈕。
必須同時顯示假設（房價 ¥5,000、200 次模擬、貪心演算法是下界）。

## 4. 設計要求

- 手機可用（經營者常在櫃檯用手機看）
- 深色 / 淺色都要正常
- 首頁載入 < 1 秒，bundle < 150KB
- 全繁體中文介面，術語附英文（stranded bed 這類概念要在 tooltip 解釋）
